# Module packages and catalogue

The hub is version 1.0.0. Catalogue schema 1 contains `SchemaVersion: 1` and `Modules`, a list of manifest objects. Property names are PascalCase. Each manifest requires `Id`, `Name`, `Version`, `EntryPoint` and the package `Sha256` to install. IDs are lowercase ASCII letters followed by up to 63 lowercase letters, digits or hyphens; Windows device names are forbidden. Versions have three or four numeric components. EntryPoint is a relative slash-separated `.exe` path.

Defaults: Kind=process, Preview=notes, MinHubVersion=1.0.0, EnableArgument=--enable, DisableArgument=--disable, StatusArgument=--status. Kind accepts process/fix; Preview accepts mixer/notes/fix. Description and PackageUrl may be empty. An empty PackageUrl describes a local/bundled package, never an invented release. SHA256 is 64 hexadecimal digits; it is mandatory at install time.

The only remote catalogue is `https://raw.githubusercontent.com/KirrieD/HUB-ReFIXwin11/main/catalog/catalog.json`. Only explicit Refresh contacts it. Remote absence, errors and malformed catalogues retain the complete local catalogue and explain the failure. A successfully validated catalogue is cached in the data root. At startup the cache is tried first, then the bundled catalogue. Release PackageUrl values must be HTTPS assets under `github.com/KirrieD/HUB-ReFIXwin11/releases/download/<tag>/<asset>.zip`. Redirects are limited to GitHub and its HTTPS release asset host. Hashes verify integrity against the catalogue; they do not establish an independent publisher identity.

Place real built archives in `<application base>/packages/<id>-<version>.zip`. The backend also checks packages beside the supplied catalogue and beside its parent directory, supporting repository development. Archive contents are relative files, including EntryPoint; do not include `installed.json` (reserved for the hub). ZIPs are limited to 64 MiB compressed, 256 MiB expanded and 2,048 entries. Absolute paths, traversal, backslashes, alternate data streams, duplicate paths, Windows device names and links are rejected.

Install verifies SHA256 before extraction, stages into the module directory, hashes extracted files, writes installed metadata and atomically selects the installed version in `current.json`. Replacing a version preserves a backup until selection succeeds and restores it on failure. Failed downloads and staging directories are removed. Installation never starts a module or applies a fix. Updates refuse verified running modules and live process identities, including an unresponsive control pipe. Old versions are retained for rollback/recovery; the hub never silently executes one on failure.

NO means no verified installed package. OFF means verified installation without verified active health; Detail explains health errors. ON for process modules requires PID, UTC process-start ticks and actual executable path to match the installed entrypoint, plus a current-user scoped pipe response with matching id/pid/startedUtc and protocol 1. Shared `ModuleRuntime.PipeName(id)` supplies the SID-scoped name. Controls use newline UTF8 status/show/stop commands with bounded replies. A missing/stale identity never reports ON. The visible host requests state refresh every two seconds; the manager owns no polling timer and performs no hidden network work.

Fix executables receive a single validated enable/disable/status argument through ProcessStartInfo with UseShellExecute=false. Each command has a four-second exit limit and bounded output; status must return one JSON object `{ "id": "the-id", "state": "ON" or "OFF", "protocol": 1 }` with exit code zero. Enable/disable output uses the same schema, then the host independently requests status. No fix is applied automatically. A fix does not have a show window action.

REFiX data defaults are provided by the shared Paths API; the manager receives that data root explicitly. REFIX_DATA_ROOT is propagated to child processes. Metadata, archives and catalogue failures are surfaced through ModuleView.Detail. Explicit catalogue/install/control action failures also fault their returned Task so the UI cannot report success. Fix arguments are validated only for fix manifests. Process startup health is given a bounded five-second window. ModuleManager.Changed and ModuleView notifications can arrive on worker threads: UI callers must marshal to their dispatcher. All operations are serialized. Dispose prevents queued work from starting; already running bounded operations finish.

Backend tests are callable as `BackendTests.Run(Action<string,bool>)`; defining BACKEND_TEST_RUNNER builds a standalone runner. Compile with the shared assembly and Framework references System.Web.Extensions, System.IO.Compression and System.IO.Compression.FileSystem. Tests use disposable data beneath the working directory's artifacts folder, because sandbox temp paths may deny directory renames.

`BackendTests.RunIntegration(Action<string,bool>)` or standalone `BackendTests.exe --integration` uses the real built artifacts/catalog.json and quick-note package in an isolated artifacts data root. It verifies install OFF, actual control-pipe ON, show, active-update rejection, stop OFF and stale identity OFF. Run outside the app-container sandbox so the child and caller share current-user pipe access. It never reads or changes the real default data root.
