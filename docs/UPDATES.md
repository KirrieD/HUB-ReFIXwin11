# HUB updates

## Module updates from 1.3.0

The Update action is available for installed ON and OFF modules. HUB downloads and verifies the candidate before stopping a running module. It then requests a graceful stop, promotes the staged files, verifies the new process and publishes its installed version. A previously running utility restarts and opens; an OFF utility remains OFF. Failed activation restores the previous files and running state. Process identity is checked before control commands; unrelated processes are never terminated. External updates must still belong to a currently configured source and match the installed module's origin. Updating HUB itself does not automatically replace installed utility packages.

HUB 1.1.0 checks once on startup and when the user selects **Проверить обновления**. It reads the fixed public GitHub latest-release API for `KirrieD/HUB-ReFIXwin11`, locates `update.json`, and offers a newer version. Acceptance is required before downloading. Cancel leaves the running installation unchanged. The first upgrade from the old 1.0 executable requires a manual ZIP or Setup upgrade.

Metadata schema 1 contains `Version`, `PackageUrl`, `Sha256`, `SetupUrl`, `SetupSha256`, and `Notes`. Package and Setup URLs must be HTTPS assets of this repository. Metadata is limited to 1 MiB; archive download to 128 MiB; expanded content to 512 MiB and 4096 ZIP entries. GitHub asset redirects are explicitly checked against HTTPS GitHub asset hosts, with bounded redirect count and timeouts. No credentials are used.

The accepted portable ZIP is hashed before extraction. Extraction accepts the release archive's single `HUB-ReFIXwin11/` wrapper (or a flat bundle), rejects mixed roots, traversal, device paths, alternate streams, duplicate names and links. Every file must be listed in `bundle-files.json` (schema 1 with `Version` and `Files` containing `Path` and `Sha256`), except the manifest itself. Windows manifest separators are normalized before validation. The manifest uses the same required file set as Bootstrap, including both executable configs, catalog, documentation, install tools and the exact known module packages. Catalog module versions and package hashes must match the bundle. `installation.json` is reserved and cannot appear as a bundle-owned file.

Preparation writes an isolated `dataRoot/updates/<unique-id>/payload` and `plan.json`, outside the application directory. The plan records target, staging directory, bundle manifest hash, release version and current Core PID, UTC start time and executable path. StartApply validates this identity and copies the current manifest-verified helper into the work directory before launching it. The caller then exits.

The independent helper waits up to 60 seconds for this exact parent to exit and never kills it. It validates paths, rejects reparse points, and verifies the prepared manifest and payload again before writing. It backs up all files owned by the old/new manifests, copies new owned files, removes obsolete owned files and verifies the resulting bundle. Existing unknown-file collisions reject the update. Unknown files remain intact. An existing Setup marker retains its fields and advances its Version within the same backup/rollback transaction, so Bootstrap continues to recognize the installation. If copying fails it restores touched files from backup, including the exact original marker bytes. Backups and error details remain in the staging directory for diagnosis; failed rollback reports that repair is required. Bootstrap restarts after successful installation or rollback. A parent-identity or exit-timeout failure leaves the still-running application alone.

`src/UpdateHelper/UpdateEngine.cs` is compiled into Core and tests as source and into `ReFix.UpdateHelper.exe` alongside `Program.cs`; the helper has no Shared DLL reference. Tests use isolated fake application directories and injected copy failures, with no registry writes, real installation changes or application launch.
